\section{Technology}
\label{sec:technology}

When you start developing a piece of software of any kind, you have to pick a stack, that being: choosing which
technologies you're going to build your project on top of. This choice is probably the single most important decision of any
project (right after choosing what to build); getting this wrong can lead to headaches for months to come.

This project experienced two major rewrites, where I swapped platform! The back-end, where the \textit{real calculations}
take place is written in "Go" (commonly referred to as Golang). Golang is like if
Python (Tygerjython) and C \footnote{The "C" programming language is the basis of most modern software infrastructure,
	being used extensively by every major operating system. It's very performant, however it has very few features, making the developer have
	to develop many things in it from scratch.} had a baby; it has a simple syntax like python with 90\% of the performance of C.
The front-end (what the user actually sees) was originally written in HTML, CSS \& JavaScript\footnote{
	HTML, CSS and JavaScript are the three main technologies that power websites. HTML provides the document content, CSS provides styling and
	JavaScript is responsible for interactivity.
} using "Wails"\footnote{Wails is an application framework that allows developers to easily develop native desktop apps using
	web technologies on the front-end and Golang on the back-end.} to connect
the front- and back-ends. A few months into development I was experiencing too many issues with this setup: random
crashes, tight coupling \footnote{Coupling in software refers to how when one part of the software is changed, another
	related part also has to be as well. } and unexplainable bugs. This frustrated me to such an extent that I stopped
working on the project for multiple weeks. Eventually, I decided to completely rewrite the front-end in Godot, a free
game engine. The problem? I didn't know Godot. The smallest of changes required hours of reading the docs and struggling
around.

In the end, I came back to my senses and tried developing the front-end in JavaScript, this time learning Web-Sockets implement
the Inter-process communication (further explained in section \ref{subsec:ipc}).
As any developer knows, the 4th time you write something is always better than the first two times. And so I stuck with
this version right until the end.

\subsection{Implementation Details}

The implementation of each of the game's parts strongly follows the principle of separation of concerns; driven by
what I learned through the game's 4 iterations.

Over time, the game was split into 3 distinct modules:

\subsubsection{The Server and Simulation}

The simulation, out of all components, has had the most longevity, not having been replaced or completely rewritten a
single time. The problem is that the simulation is really just a library with little ability to be played or interacted
with on its own.

To fix this, I added \textit{the server}. The server (also referred to as the game server) uses the "simulation"
library and acts as an interface between the front-end and the simulation: it transmits data between the simulation and
the front-end, caches user state to prevent users from having to redo all their changes if anything goes wrong between
simulation steps, it sanitises input (makes sure no bad input gets into the simulation) and handles connections, saving
/ loading and some other functions.

\subsubsection{User Interface}

The problem of being able to interact with the game is not completely solved thanks to the server; unless you like
typing out commands into a terminal.

Especially in the realm of video games, there are many ways to display a graphical user interface and with each solution
you can \textit{eventually} reach the same end goal. Since I had never
planned to have complex graphics that would require direct access to hardware, the main factor for deciding which
technology to use is how well I know it. Every technology has its quirks and its share of weirdness, and I after
struggling with Raylib,\footnote{From \href{https://www.raylib.com/}{https://www.raylib.com/}: "Raylib is a simple and
	easy-to-use library to enjoy videogames programming."} Dear ImGui \footnote{From
	\href{https://github.com/ocornut/imgui}{https://github.com/ocornut/imgui}: "Dear ImGui is a bloat-free graphical user
	interface library for C++." Note:  ImGui has bindings for other languages} and even Godot game engine,\footnote{Godot is
	a free and open source game engine similar to Unity or Unreal Engine. It's an integrated environment for developing
	games and comes with many tools to simplify the game making process} I settled for what I know, even if it isn't
necessarily the "best tool for the job".

For the web interface, I chose the SvelteKit framework for JavaScript. It is a front-end web framework with a relatively simple syntax. It's very
powerful and is extremely performant thanks to the fact that it compiles to regular JavaScript, HTML and CSS.

When using SvelteKit or any other web-based framework, you also need to have a web server to serve the layout to a
browser, which brings us to the final component:

\subsubsection{The Orchestrator}

The orchestrator ties everything together. It bundles everything the game needs to function into a single binary with an
embedded file system. When it is run it writes the contents of its file system (the game server, web server, assets and
some supporting files) into a temporary folder and runs both servers. When you are done playing (or one of the servers
crash), it cleans up after itself and deletes any files it created. Thanks to tools provided by Golang, this system
also makes it incredibly easy to compile versions for all operating systems at once.

\subsection{Web-Sockets and Inter-process communication}
\label{subsec:ipc}

One of the first non-trivial problems you experience when using multiple programming languages is how to send data from
one program to the other. This is especially relevant in the context of this game because it has 3 separate processes
running simultaneously (the web server, the game server and the orchestrator).  This is where Inter-process communication (IPC) comes into
play and thanks to modern operating systems, there are many ways to share data between programs. Some of the most common
are signals, sockets and pipes; all these systems are universally available, able to transfer data asynchronously\footnote{
	In programming, synchronous operations refer to operations where the program just has to wait for the operation to finish,
	not able to do anything else while waiting. Asynchronous operations allow the program to do other things while waiting for
	operation to complete, when the operation is complete, the program finished handling it. \label{footnote:async}
} and are used in this project, however not all are suited to all tasks. To understand which method to use for what, we need to understand
what they are.

The simplest IPC is probably the signal. Signals are sent through the operating system, interrupt the program at a
certain point and run some function (by default exiting the program). What is done when a signal is received has to be
defined by the recipient in advance. For example, when you close a program you send the "kill" signal, the
execution of the program is interrupted and the defined action is run; this typically entails saving unsaved data and
cleanly stopping the program to make sure no data is corrupted. The orchestrator uses signals to know when to close
both server and clean up. Signals, while practical, aren't very useful for transferring larger amounts of data than a "kill" signal.

Far more versatile are pipes. Pipes are buffers (shared memory) that one process can write to and the other can read from. Imagine
someone sharing their screen on a call, the other person can see what's happening but can't edit what's happening. So
for two process to have a two-way communication channel, they need two pipes: one to the other program and another from
it. The main advantage of pipes is that they are simple to implement, thanks to the fact that the operating system
does most of the heavy lifting. Pipes are also often used by sysadmins to chain commands together: for example, on MacOS
or Linux. You can get a sorted list of files in a folder by entering \texttt{ls | sort}: this runs the "ls" program,
which lists the files in a folder then \textit{piping} its output into the "sort" program. Pipes are a really useful tool to
understand if you regularly use the command line. They are also used in the orchestrator to forward log messages from
both servers. They are unsuitable for communication between the front-end and the game server as they only work on the
machine locally and cannot communicate to other machines.

The most versatile IPC (in my opinion) are sockets. Sockets use the network\footnote{Most devices, as well as having network
	connections to other computers, also have a \textit{loop back} network, which enables the use of sockets for communication
	between two processes on the same machine.} to receive data using internet protocols such as TCP\footnote{TCP (Transfer
	control protocol) is a protocol used by most internet applications. TCP has robust error checking and automatically
	re-requests dropped packets (information that didn't make it to its destination). \label{footnote:tcp}} or
UDP\footnote{UDP (User datagram protocol) is a lean, "best effort" protocol for sending data over the internet.
	It does not check for errors or dropped packets. UDP is primarily used in real-time applications where it's OK to
	drop some packets, like gaming or streaming.}.
Sockets are like a letterbox in a large office: each employee has an assigned letterbox and can receive letters
from the internal mail service or by post. These letterboxes are called ports, and only a single process can own a given
port but can receive messages from many processes. Using sockets a program can also receive data from other computers on the
network: for example when you open a website, your browser sends a packet (like a letter) to the server on port 443, along with
written in the packet there is a return port (e.g. 31222), the server then replies with a packet containing the data that was
requested and sends it to the port written in the request. This is the method used heavily in Wisim. The great thing about sockets is
that there is a huge amount of tools built on top of it, specifically for this project I'm mostly using Web-Sockets.

Web-Socket is a protocol built on top TCP that allows for the easy creation of a 2-way data link between a server and
a browser\footnote{For more information on Web-Sockets see \href{https://en.wikipedia.org/wiki/WebSocket}{https://en.wikipedia.org/wiki/WebSocket}
	for general information or \href{https://developer.mozilla.org/en-US/docs/Web/API/WebSockets\_API}{https://developer.mozilla.org/en-US/docs/Web/API/WebSockets\_API}
	for usage details}. They use a socket on both the client and server, and they are able to bypass what I like to call the "port
problem": namely that the server is (usually) not allowed to query the client. \footnote{Typically, the firewall on the
	client device will block all incoming connections unless they are replying to a client request.} It does this by having
the client send an HTTP\footnote{HTTP (Hypertext transfer protocol) is a protocol built on top of TCP\footref{footnote:tcp} used
	mostly to transmit data about websites.\label{footnote:http}} request to the server, the server then "upgrades" the request to a Web-Socket and instead of
replying and closing the connection, the server just leaves it open. Web-Sockets are by far the easiest way to get a full-duplex
(bi-direction) connection between a web-browser and a server.

\subsubsection{Implementing Web-Sockets}

While Web-Sockets are very simple to implement, they have a totally different \textit{data-flow}\footnote{What is referred
	to here as \textit{data-flow} is the order in which different parts of a program access data. Typically data is
	set then it is used. The asynchronous\footref{footnote:async} handling of data with Web-Sockets forces the developer to rethink how / when data
	is used and when it is deemed invalid.} compared to HTTP:\footref{footnote:http} on the client
you usually make an HTTP request and await a response, this is quite easy to implement, when you need data you ask for
it and wait. With Web-Sockets, you have to implement asynchronous\footref{footnote:async} event handling because you never know when the server
is going to send a new message.

On top of the previous, Web-Sockets is a binary format, that means that messages are not cleanly formatted like in HTTP
with designated headers and status codes, instead they are just raw text: how the data is formatted is up to the
developer. With me being \textit{the developer}, that gives me a lot of room for stupid decisions. For example, I spent a
day inventing my own data encoding protocol which mimicked a command prompt. This might not sound all that dumb until
you realise that both JavaScript and my Go back-end include functions for parsing JSON\footnote{JSON (JavaScript
	Object Notation) is a plain text data encoding format often used on the web. For more information see
	\href{https://en.wikipedia.org/wiki/JSON}{https://en.wikipedia.org/wiki/JSON}} encoded messages.

\subsection{WebAssembly}

Since the game has some parts written in Go and some in JavaScript, there will almost inevitably be some code that needs
to be shared between the languages, lest I code 2 versions of the same function and \textit{try very hard} to keep both versions in sync.
For example, the \verb|CalculateProductStats| function, which is used to (now this is going to surprise you) calculate the
properties of products. This function has to be identical on the front and the
back-end, otherwise players might get misled into thinking that their products are more or less good than they really
are. Thankfully, other people have already had this problem and even came up with a solution. The solution, as you might
guess by the section header, is called WebAssembly.

WebAssembly is a runtime for running non-JavaScript code on the browser. It is designed as a compile target for other
languages so that they can run in a standardised, architecture agnostic\footnote{Every CPU is based on a certain Architecture, such
	as ARM or x86. Code built for ARM cannot run on x86 or vice versa. What WebAssembly does is that it translates
	WebAssembly code to compatible machine code, either just in time or ahead of time } way inside a
browser. This means that programming languages that typically can only run native platforms like C and Golang
can run with \textit{near native} performance\footnote{When talking about WebAssembly, "near native" performance refers
	to programs compiled in WebAssembly running near their native speed running directly in the operating system (instead of in the browser) for
	compute tasks. Tasks that involve interacting with the structure and style of the website are still much slower than in JavaScript.}
in a browser.\footnote{For more info on what WebAssembly is and how it works, see:
	\href{https://developer.mozilla.org/en-US/docs/WebAssembly}{https://developer.mozilla.org/en-US/docs/WebAssembly}}
